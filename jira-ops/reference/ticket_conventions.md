# 單型慣例與流程 Knowhow（全部從真單歸納；每型附實例單號可回看）

## 0. 通用硬規範（先讀，優先於一切）

1. **開單前五層閘門**（逐條需求過，過不了不進第一階段；來源＝32708 亂開單教訓）：
   ①需求層＝這條是作者/用戶原話還是我推導的？推導的標「提案」降級
   ②資料層＝資料源存在？契約支援（欄位/日期/批次）？**先自查**（cmf skill/源碼/wire），契約不支援就別寫依賴它的需求
   ③邏輯層＝判定/邊界/fail 行為 PM 定死才准寫
   ④呈現層三問＝顯示什麼？在哪？**用戶看到能做什麼決策？第三問答不出＝不顯示**（反例：「資料待更新」逐檔標籤——fail-open 是邏輯層防呆，不自動升級成 UI）
   ⑤範圍/權限層＝沿用哪個既有架構？查現況寫「比照現行XX」具體指認。**上游對話措辭≠產品事實**——寫「與既有XX組合」前先對畫面或程式碼確認 XX 真的存在（反例：驗收寫「勾選KY」但篩選器根本沒有 KY 選項）
2. **MVP 切分**：行為核心（開關＋邏輯＋保存＋fail-open）＝第一階段；呈現統計類（標籤/檔數/日期/原因標示）＝第二階段另出規格。**一張單只放 RD 拿了就能做的內容**——待設計項寫成需求＝把 PM 沒做完的工作外包給 RD 盤查。
3. **機器研判段免責句**：範圍研判/根因分析/平台歸屬/派工建議等機器推斷段，段尾固定加「（此為機器依票面資訊做的初步分類建議，非人工判定，請 RD 覆核後修正。）」
4. **不得擅發「要求別人做事」的內容**：單內/留言「請 RD 回覆/請確認/請提供」段，未經 PM 本人允許不得發布。先自問「我自己查得到嗎」——查得到就查掉預填，查不到留草稿標 ⚠ 由 PM 決定怎麼問。
5. **到期日必填**：沒給就開單前問一句；「下週五」先跑 `date` 換算絕對日期。
6. **語氣**：全線原則＝**協作不裁決、明確不模糊**（owner 2026-08-27 定版）。評估型/優化型需求寫「商量感」（「不急、未排期，先請你評估」「構想方向供評估參考」）；**驗收回饋用「完成/需調整」，不用「通過/未通過/退回」等裁決究責詞**，做得好的項目明確列出肯定；不確定的直接寫「請協助評估、可共同討論」；**不加**過度親暱開場白（自然問候＋謝謝即可）。驗收標準**寫白話場景**，GWT 術語保留給正式功能故事單。
7. **預期結果一律寫成「情境序列＋正反例」**（開單與驗收回饋皆然）：①**如何觸發／使用情境**——使用者在哪、做了什麼；②**每一步預期發生什麼**——操作→畫面→再操作→畫面（非預期行為同樣逐步寫：「預設不顯示，需長按後才顯示」）；③**希望是什麼＋不是什麼＋實際範例**（「顯示日期 如 2026/08/27，而不是當天時間/X 天前」）。只寫結果名詞（「顯示正確」）＝RD 要用猜的。
7. **開單前查重**：`--jql "summary ~ '關鍵字'"` 先掃，已有單＝留言補充非重開。

## 1. Bug 單（PROJ 漏洞）

- Summary：`【BUG】【{平台}-{作者}】{問題簡述}`（衍生優化用 `【優化】【{平台}-{作者}】…`）
- 描述七段（ADF 色塊）：背景/回報來源（來源連結硬規範：每張單必有一行 `來源:<可點連結或明確出處>`）→客戶資料（帳號/MemberID/機型/版本/觸發時間路徑）→重現步驟→實際結果→預期結果→範圍研判（＋免責句）→附件說明（**必附截圖或錄影**，沒有標 ⚠附件待補）
- 必填：影響版本（最大版動態查）＋Bug 來源＋Sprint＋五評估欄位初估
- 實例：TICKET-1000（CS 轉單）、32904（PAGEs 修正）

## 2. 故事單三張套裝（雙平台需求）

- **主單（雙平台）＋iOS＋Android 各一張**，議題分割關聯（inward=主單）
- **平台單描述＝主單完整複製＋平台標註，不是精簡版**（RD 只讀自己那張就能動工）；主單＝canonical 規格＋作者變更追記處；長技術細節放留言
- 描述七塊骨架：背景/目的/需求（可施作條目）/接受標準/相關連結（資料源 id 預填＝頭號防來回）/範圍框「✅包含/❌不包含」/[User Story]
- 純後端＝一張後端單；確定單平台＝一張
- 實例：TICKET-1000/16/17（含附件 API 上傳）、29381/82/83

## 3. CS 客服單處理（CSUCCESS → PROJ）

1. **讀單必帶 attachment 欄**（CS 常有用戶錄影，漏看會誤標「附件待補」）
2. **處置四型**：轉開發單／快速設定修（remote config 解掉、留言記錄不開單）／觀察自癒關單／個案 won't
3. 轉單：PROJ 開完整 bug 單（背景引 CS 單號＋起始版本＋客訴量）；附件用 `jira_api.py copyatt` 原檔搬運
4. **CS↔開發單掛 Relates link**（機械判斷「已轉單」的依據）
5. 回寫 CS 用範式：`【進度更新｜PM XXX】已完成根因分析並開立 RD 修正單。根因:…。處理:…。iOS:KEY/Android:KEY。後續:待 RD 排程,上線後更新。`修復上架後回「x.y.z 已調整後上架」帶版本號
6. CS 單＝同症狀聚合點（客服會追加同類回報，別重複開單）
- 實例：TICKET-6000 → TICKET-1000；範式參考 TICKET-6000 → TICKET-3000/8（Fischer）

## 4. QA 送測與追蹤

- **QA Task 開在 OPS**：標題 `{App}_APP回歸測試 (iOS/Android)-{主題}`，指派 QA（蔣明廷），描述 markdown 含測試版本表＋本次重點單清單，Blocks 對應需求單
- **追 QA 進度＝雙軌**：①UTILITY QA Task 狀態（待QA測試→QA測試中→QA已完成）②AUTHOR Stage-bug＝QA 邊測邊開的產物（`issuetype=Stage-bug AND summary ~ '{作者}'`）
- **「送 QA」≠「發驗收」**：發驗收＝RD 發包給 PM 驗（單進「等候驗收」）；送 QA＝OPS 回歸單。OPS 標題＋全文雙查 0 筆＝沒開單，別假設在測
- Stage-bug 轉正式 bug：Cloners 關聯＋附件搬移
- 實例：TICKET-2000（Product B 2.6.0 對齊版回歸）

## 5. PAGEs（公版）修正票兩流派

- RD 說「開 PAGEs 修正的票」→ **一樣開 PROJ**：
  - **作者線發現**（RD 自請）：標題 `【BUG】【iOS-PAGEs-{作者}】`、parent＝發現問題的作者 Epic、Bug 來源＝內部通報、components 留空、**影響版本掛 PAGEs 公版版號**（如 PAGEs_iOS_3.54.0，非作者 App 版號）
  - **PAGEs 產線流**（產線 PM 收單）：標題 `【PAGEs 平台-{作者} {平台}】`、不掛 parent、components＝平台RD＋「PAGEs 國內潛力」
- 判流派看「誰發現、誰要修」
- 實例：TICKET-1000、31669（RD-iOS 流派一前例）

## 6. 其他單型速記

- **Crash 掃描**：一張薄母單「新Crash事件_YYMMDD」，RD 自拆子單，PM 不逐項開 N 張
- **EDMIS**（Server/DB 申請）：填表單自動開單；查自己申請過什麼＝`reporter=currentUser() AND created>=-Nd`；小量 OLTP 申請 Redis 會被 DBA 導改共用 PostgreSQL
- **衍生單**（修完發現新問題）：新單＋Relates 原單＋指派**原修復者**；症狀與根因層跟原單相同→退回原單，**不同→開新單**，別塞進原單搞混修復範圍

## 7. 驗收回饋格式（貼在單留言）

- 標準三段：【重現步驟】【實際結果】【預期結果】；後修狀態用【驗測回報】/【驗收回饋】開頭
- **部分修復**：標題先給結論「主路徑已修＋剩餘項不擋送審」；用戶發現的 workaround 升格成獨立「重現條件線索」段（那是 race condition 的黃金線索）；優先序寫成明確排程指示（「X 照送審、先做 Y、本項排其後」）
- **雙平台同症狀**：各貼各的平台單＋互引單號＋兩邊都寫「請雙平台討論對齊」；兩端症狀不同分開描述
- deep link/分享類驗收固定測「App 冷啟 × 熱啟 × 內容類型」矩陣
- **多項單（一張單N個修正項）的驗收回饋六鐵律**（範本=TICKET-1000 定稿,owner 2026-08-27 定版）:
  ①**結論先行、協作語氣**:第一句寫「N 項中幾項**完成**、幾項**需調整**」——用「完成/需調整」,**不用「通過/未通過/退回」等裁決究責詞**;開頭一句自然問候+謝謝(「Hi @XX！這邊是驗收回饋,謝謝你!」),完成的項目**明確列出並肯定**(哪些做得好),不是只列問題
  ②**非預期行為寫成「每一步發生什麼」的序列**:不是一句「沒顯示」,而是「預設不會顯示 DIF/MACD 參數,**需長按後才會顯示**」——操作→看到什麼→再操作→看到什麼。原單規格用引用不重貼;**改寫他人觀察不得偷換原句主詞**(反例:「時間顯示未依由近到遠」主詞=標籤格式,被改寫成排序缺陷);沒實測過的細節標「待實測確認」不寫成觀察句
  ③**疑似新問題,先做「草稿 vs 原單描述」逐段比對再判**:原單本來就有=既有範圍照驗不拆單(反例:32216「延伸」段誤判成新發現);確認真新發現才判層——同根因層退回原單、不同層另開單＋Relates
  ④**預期寫成「希望是什麼＋不是什麼＋實際範例」**:正反並列防誤解——「希望顯示新聞日期(**如 2026/08/27**),而**不是**當天時間/X 天前」;只寫正面敘述=RD 可能做出字面正確但不是你要的東西
  ⑤**PM 能拍板的當下拍板;技術可行性不確定的,明說請 RD 評估、可共同討論**:「希望協助評估技術上能不能與 Android 對齊皆顯示日期」——偏好與範例寫死(方向不模糊),可行性交給專業(不越權裁決);不得把純呈現偏好模糊成「二擇一你選」丟給 RD
  ⑥驗收標準必須**可判定且含範例**:每條讀完能直接勾「過/不過」(「顯示日期 如 2026/08/27」);依賴未收斂選項或「規則一致」這類抽象詞=不可驗

## 8. 常用查詢 JQL

```
# 我剛剛轉完成/動過狀態的單
status changed by currentUser() during (-4h, now())
# 某人通報、我轉完成的
上式 + 逐張看 reporter
# 追某作者未結單
project=PROJ AND parent=TICKET-1000 AND statusCategory != Done
# 用症狀反查單號(使用者只給描述沒給號)
project=PROJ AND summary ~ '<關鍵字>' AND statusCategory != Done
```
