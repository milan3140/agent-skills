# ASCII Prototype 先行(佈局提案的強制閘門)

寫規格文件或程式碼**之前**,先用 ASCII 排出多個佈局候選給使用者挑。
出處:2026-08 Sara CB 桌面版三欄工作區實戰——使用者指示「用 ASCII 產出多個最佳候選讓我看」,
挑定後一次到位;對照過往「直接實作再改」的返工成本,ASCII 十分鐘 >> 重寫三輪。

## 時機(何時必須做)

- 資訊架構/佈局存在 **≥2 種合理方案**時(單一顯然解不用)。
- 對標研究(標準流程步驟 2-3)之後、產出規格文件(步驟 4)**之前**——先有 Best Practices 再排版,不是憑空畫。
- 使用者挑定(可混搭修改)後,才進規格與實作。**沒挑定不動工。**

## 產出規則

1. **2~4 個候選**,每個代表**不同的互動模型**(例:三欄常駐 vs 兩欄+抽屜 vs 專注模式+浮層),不是同版型的裝飾微調。
2. **依真實比例排版**:框寬對應真實欄寬,標註尺寸(px 或 fr)與斷點(≥1280 / 840-1279 / ≤839)。
3. **區塊內寫真實內容**:欄位名、按鈕字、資料範例——不是 lorem 或「內容區」。
4. **標互動 affordance**:可拖曳邊界(║⋮║)、hover 展開(⇄)、收合 rail(▏)、橫向捲動(⇢)、固定/浮動。
5. **每案附兩行**:一行「設計立場」(這個版本在賭什麼),一行「取捨」(得到什麼/犧牲什麼)。
6. RWD 是議題時,**每個斷點各出一張**(手機若凍結不動就明說「手機版不變」)。

## 畫法規範

- Box drawing:`┌ ─ ┐ │ └ ┘ ├ ┤ ┬ ┴ ┼`;雙線 `║ ═` 保留給「可拖曳邊界」。
- 總寬 ≤100 字元(聊天視窗不折行);高度抓重點,長列表用 `…` 截斷。
- 等寬呈現:輸出時包在 code fence 內。

## 為什麼是 ASCII(不是截圖/Figma/HTML mock)

- 聊天內即時可看、可逐字修改討論,迭代成本趨近零。
- 逼迫聚焦**結構與互動模型**,不被顏色字體帶走(那些是 token 階段的事)。
- 使用者一眼可比對多案;挑定後 ASCII 圖直接貼進規格文件當佈局藍圖。
