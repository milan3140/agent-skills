# PRD 必要元素清單（供 /spec-grade 打分使用）

本檔為單一 source of truth。任何一條元素的定義／評分規則變更，`/spec-grade` 打分規則同步更新。

---

## 使用說明

- **總條數**：**14 條**，每條 0/1/2 分，**總分 28 分**
- **通過閾值**：**22/28（≈79%）**
- **N/A 規則**：spec 未涵蓋的平台，對應條目自動 N/A（不計分、不列入總分基準）
  - Android-only → §10 (iOS) N/A，總分基準降為 26、通過線 21
  - iOS-only → §9 (Android) N/A，總分基準降為 26、通過線 21
  - Web-only（未涵蓋任何 mobile 平台）→ §9 §10 皆 N/A，總分基準降為 24、通過線 20
  - 跨平台 spec → 依實際涵蓋平台判定
- **評分嚴格度**：以「**測試員讀完能不能開始跑測**」為判定標準
  - **完整(2)**：資訊具體到位、可直接執行測試
  - **部分(1)**：有寫但缺關鍵細節（測試員仍需回頭問 PM）
  - **缺(0)**：完全沒寫，或只有一句空話

**團隊分工前提**（哪些不進 checklist、原因；**以下為本團隊（Product X/App QA）的分工假設，其他部門若團隊組成不同——例如全端 QA、無內部 debug 工具、純 Web 團隊——可視情況豁免對應扣分**）：
- **註冊流程 / 帳號建立步驟**：屬 QA 自己的操作知識（有既存 helper 腳本 / 共用測試帳號等）；PM 不需寫進 spec
- **後端 API 細節（endpoint、mock、cron 時間）**：本團隊 QA **只驗前端**；後端交付驗證由 RD / 後端 QA 負責（若你的團隊是全端 QA，可自行加碼要求 PM 寫）
- **RC 生效方式（pm clear + SSO 重登）／內部 debug 工具 UI 入口位置／Build 類型（debug/release/Beta）**：QA 操作 SOP，非 spec 內容
- **AC 中的實作語言類名／術語**（Kotlin / Swift / TypeScript 等）：AC 主要是給 RD 看的實作契約；QA 讀 Scenario 描述的行為即可，不需要求 PM 為 QA 另翻譯

## 元素定義

### A. 範圍界定（3 條 = 6 分）

#### 1. 變更範圍與改動類型
- **完整(2)**：具體列出改哪些**畫面／功能／模組**，並標明每項改動類型（新增 / 修改 / 移除 / 重構）
- **部分(1)**：只寫「改 X 功能」但無畫面／模組層級細節；或漏標改動類型
- **缺(0)**：無範圍章節或只有一句空話

**測試員為何需要**：知道回歸驗證範圍、知道哪些是新功能一次驗、哪些是修改要比對前後

#### 2. 不做的事（Out of scope）
- **完整(2)**：有專屬 Out of Scope 章節，明確列出**不做的相鄰議題**（尤其容易被誤解為「應該一起做」的部分）——一般以 ≥ 3 條為原則；若本次變更範圍極小、確實無足以列出的相鄰議題，明說「本次無 Out of Scope」亦算完整
- **部分(1)**：只有一句「其他不動」帶過，或散在文中沒集中列出
- **缺(0)**：無 out of scope 章節

**測試員為何需要**：避免誤把相鄰議題當本次驗收範圍，浪費時間跟 PM 對來對去

#### 3. 相依既有功能與回歸範圍
- **完整(2)**：列出這次改動**連帶影響哪些既有功能**（回歸驗證清單）；若無影響也明說「不影響任何既有功能」
- **部分(1)**：文中零散提及、無彙整清單
- **缺(0)**：完全沒提

**測試員為何需要**：規劃回歸測試範圍、避免主流程過了但相依功能壞掉

---

### B. 前置條件（1 條 = 2 分）

#### 4. 使用者狀態與帳號 tier
- **完整(2)**：具體列出**每個驗收情境要對應什麼 state**——以**本產品實際存在的 state 分類**為準；只要涵蓋本次變更會觸發不同分支的所有 state 即算具體
  - 範例（產品中立）：訪客／已登入／首次啟動／老用戶回訪／付費會員／已購買特定商品／試用中／試用到期
  - 範例（有會員分層的產品，如Product X）：Plan A/D 試用中／已購買 VIP／試用到期後 30 天
  - **判定原則**：若該產品無會員分層（無 tier 概念），寫「已登入」「新註冊用戶」即為具體，不需硬套 tier 用語
- **部分(1)**：講了角色但**遺漏本次變更會觸發不同分支的 state**（例：功能對「首次啟動 vs 已看過教學」行為不同，PM 只寫「已登入使用者」）；或用「一般帳號」這種在該產品內仍有歧義的模糊詞
- **缺(0)**：完全沒說使用者狀態

**測試員為何需要**：不同 state 觸發不同分支，state 不明會導致測試根本觸發不了目標行為

---

### C. 設定參數（2 條 = 4 分）

#### 5. Remote Config 參數
- **完整(2)**：
  - 列出所有涉及的 **RC key 名稱**
  - 每個 key 要**改成什麼值**（含 JSON 範例或明確描述）
  - 值的**來源**（PM 自填 / 從既有配置抄 / 需 RD 提供）
  - 是否需要 override 特定 Firebase condition，還是改 baseline
  - **實驗／A/B test 干擾說明**：若該 key 目前被 Firebase A/B test 或其他 experiment 掛住（測試帳號可能被分到 experiment variant 而拿不到 PM 想驗的值），需明說：
    - 該 key 是否有 running experiment / A/B test
    - 若有，測試帳號如何避開 experiment（例：改 condition targeting、關掉 experiment、指定特定 user segment）
    - 或明確標「本次驗證需先暫停 experiment X」
- **部分(1)**：只提「透過 RC 控制」但沒給 key 名 / 值 / 來源；或有寫 key/值但未提實驗干擾
- **缺(0)**：無 RC 章節

**測試員為何需要**：不知道要改什麼 key、改成什麼值 → 環境完全準備不起來；被 experiment 擋住的話 PM 設什麼值 QA 都測不到，會誤判 bug

#### 6. 前端內建預設與 fallback
- **完整(2)**：明確說明「若 RC 未下發／查詢失敗／解析失敗，App 端行為為何」（例如「無下發 → 靜默不發任何提醒」）
- **部分(1)**：只講 happy path、無 fallback 說明
- **缺(0)**：無 fallback 章節

**測試員為何需要**：驗容錯路徑要有明確預期，不能靠猜

---

### D. 埋點與觀察（2 條 = 4 分）

#### 7. ELK 事件
- **完整(2)**：
  - 列出**新增或改動的事件名**（依該產品埋點命名慣例，如 `UPA_XXX_YYY` / `evt_xxx` 等）
  - 每個事件的**觸發時機**（哪個 UI 動作、哪個狀態轉移觸發）
  - 每個事件的**關鍵屬性**（params：如 `from`、`remaining_minutes` 等 QA 需要 check 的欄位）
  - **事件間的漏斗關係**（如：scheduled → showed → clicked → viewed）
- **部分(1)**：只列事件名、無屬性或觸發時機；或只有描述性名稱無具體 event name
- **缺(0)**：無埋點章節

**測試員為何需要**：ELK 是前端 QA 主要驗證工具之一；不知道要 check 什麼欄位＝驗不到

#### 8. UI 可觀察行為
- **完整(2)**：驗收條件都能對應到「使用者眼睛能看到的東西」（通知標題／內文、頁面 UI、按鈕行為、彈窗文字等），**不依賴內部 log / dumpsys / 資料庫**
- **部分(1)**：大部分 UI 但個別條目仍依賴內部工具
- **缺(0)**：主要驗收條件都靠內部工具（前端 QA 無法執行）

**測試員為何需要**：前端 QA 只能驗 UI；內部工具是 RD / 自動化的責任

---

### E. 平台特定行為（2 條 = 4 分）

#### 9. Android 平台特定行為
（若 spec 未涵蓋 Android，則 N/A）
- **完整(2)**：明說本次改動涉及的 **Android 版本相依行為**：
  - Android 版本要求（如 Android 13+ POST_NOTIFICATIONS、Android 12+ 通知啟動限制、Android 14+ 前景服務類型等）
  - **若涉付費內購驗證**：是否已上傳 **Play Store Beta**（Android 內購限定，其他測試手段驗不到內購 flow）——本產品**無內購**則不適用
  - 若無 Android 特定行為需注意，明說「無 Android 版本相依」
- **部分(1)**：提到 Android 版本但無具體行為說明；或涉內購卻沒提 Play Store Beta
- **缺(0)**：spec 涵蓋 Android 但完全未提及任何 Android 平台特定行為

**測試員為何需要**：Android 版本行為差異大，PM 若明說 QA 才知道要在哪個 API level 驗；VIP 購買特別要注意 Play Store Beta 上傳

> **註**：**QA 操作 SOP**（RC 生效方式、DebugSetting UI 入口位置、Build 類型選擇等）不在此條要求範圍內——這些屬 QA 自己的知識，PM 不需寫進 spec

#### 10. iOS 平台特定行為
（若 spec 未涵蓋 iOS，則 N/A）
- **完整(2)**：明說本次改動涉及的 **iOS 版本相依行為**：
  - iOS 版本要求
  - APN / 通知權限流程差異
  - 若涉 Live Activity 等 iOS 特殊功能，需明說
  - 若無 iOS 特定行為需注意，明說「無 iOS 版本相依」
- **部分(1)**：提到 iOS 但無具體行為
- **缺(0)**：跨平台但無 iOS 章節

**測試員為何需要**：iOS 跟 Android 平台差異大，兩邊 quirk 都要明說

---

### F. 驗收與例外（2 條 = 4 分）

#### 11. AC 驗收條件
- **完整(2)**：條列所有驗收條件（AC-1、AC-2... 或 Given/When/Then Scenario 格式，openspec 亦屬此類）；每條有明確 WHEN/THEN 描述行為；可對應到 UI 或 ELK 事件觀察
- **部分(1)**：AC 章節存在但空泛、無 Scenario 結構、或條件描述含糊到 QA 無法據以寫測試案例
- **缺(0)**：無 AC 章節

**測試員為何需要**：AC 是測試計畫的骨架、QA 依 Scenario 寫測試案例

> **註**：**AC 中含實作語言類名（Kotlin / Swift / TypeScript 等）／內部術語不扣分**——AC 主要是給 RD 看的實作契約，QA 讀 Scenario 描述的 WHEN/THEN 即可

#### 12. 已知缺口 / AC 例外
- **完整(2)**：明確標示「這種情境雖行為不符標準，但屬**已接受取捨**」（如 `AC-3.1` 例外、或用該產品慣用的已知缺口編號如 `RSK-N` / `KNOWN-N`），避免 QA 誤判為 new bug
- **部分(1)**：文中零散提及但無彙整
- **缺(0)**：不做例外標示（QA 遇到會全部當 bug 開）

**測試員為何需要**：QA 若不知道哪些是 known issue，會浪費時間開 bug 單被 PM/RD 打回票

---

### G. 導航（1 條 = 2 分）

#### 13. 新增 UI 導航路徑
- **完整(2)**：若本次**新增**畫面／新增按鈕／新增進入來源，明說**如何從主頁進入**（從哪一 tab、按什麼順序點）；若不新增 UI 則明說「本次不新增使用者可見 UI 頁面／按鈕」
- **部分(1)**：有提 UI 名稱但沒說怎麼從主頁進入
- **缺(0)**：新增了 UI 卻完全沒提入口位置

**測試員為何需要**：找不到入口＝找不到要測的東西

> **註**：**DebugSetting 等 QA 操作工具的 UI 入口**不在此條要求範圍內——這些屬 QA 自己的知識

---

### H. 後端相依（1 條 = 2 分）

#### 14. 後端相依交付項與驗收環境
- **完整(2)**：本次改動若倚賴後端交付項（**新增／修改 API 端點**、**後台管理介面新增選項**、**資料表 schema 變更**、**設定檔新欄位**等），明列：
  - **後端交付項清單**（哪些 field / API / 後台選項；含對應阻塞單號如 `<TICKET-N>`）
  - **交付狀態**：**正式機 ✅/❌** 與 **測試機 ✅/❌** 分別標示（含預計 ready 時間，若尚未上）
  - **QA 驗收環境選擇**：**正式機** 或 **測試機**（**由 PM 明確指定**）——避免 QA 拿 spec 準備測時發現該環境的後端還沒 ready、白白對來對去
  - **交付狀態需在 QA 開測前再次確認**：spec 寫的狀態可能過時；發版測試當下若原定正式機但屆時未 ready，需 PM 當場決策改用測試機或延後驗收（避免 QA 依 spec 舊狀態準備、開測才發現正式機還沒欄位）
  - 若本次改動**不涉後端交付**（純前端），明說「本次無後端相依」
- **部分(1)**：有提到後端相依但未寫交付狀態、或未指定驗收環境；或明知有依賴（例如新 UI 需要的欄位、新 API 端點、方案綁定欄位）卻沒條列
- **缺(0)**：本次改動涉及後端新增／修改交付項但完全未提

**測試員為何需要**：QA 準備驗時若後端欄位還沒開（例如新 UI 綁定的資料欄位、新按鈕呼叫的 API 端點），會發現「畫面不動」或「按鈕點下去 API 400」，白白花時間對來對去；PM 明確標示交付狀態 + 環境選擇（正式機 or 測試機）就能避免這種 blocker

**範例（結構參考，實際欄位以本產品需求為準）**：本 spec 依賴後端阻塞單 `<TICKET-N>` 交付新增以下欄位——`<欄位A>`（用途說明）、`<欄位B>`（用途說明）；目前狀態：測試機 ✅（YYYY-MM-DD 已上）/ 正式機 ❌（預計 YYYY-MM-DD）；本次 QA 驗收於**測試機**執行（PM 決定：不等正式機交付即可先驗）

## 評分結果格式

```
總分：X / 28 (Y%)
狀態：🟢 通過 / 🔴 未達通過閾值 22/28 / 🟡 邊緣通過（22-23 分建議補件再送）

逐項評分（依 A~H 排序）
每項打 ✅(2) / ⚠️(1) / ❌(0) / ⚪(N/A)

補件優先建議（依缺件嚴重度）
每條「請補：<具體要補什麼>」
```
